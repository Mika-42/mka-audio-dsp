## API et migration

`DAG` devient `final`, non polymorphe, non copiable et non déplaçable. Il possède
les Node et doit survivre aux plans ainsi qu’aux utilisations de pointeurs
empruntés. Construction, éditions, compilation, collecte et destruction se font
sur contrôle, avec sérialisation externe des éditions.

```cpp
DAG(); // quota par défaut : maxNodeID objets possédés
explicit DAG(std::size_t maxOwnedNodes) noexcept;

template<class T, class... Args>
std::expected<NodeID, GraphError> add(Args&&... args) noexcept;

Node* node(NodeID) noexcept;
const Node* node(NodeID) const noexcept;
std::size_t collectRetiredNodes() noexcept;
```

`T` doit dériver publiquement de Node, être concret et constructible avec
`T(NodeID attribué, Args&&...)`. L’ID est toujours fourni par le DAG ; les autres
arguments sont transmis en conservant leurs catégories de valeurs, y compris
les références et les valeurs déplaçables non copiables. Les contraintes sont
vérifiées à la compilation.

L’ancien `T& add<T>()` devient un résultat faillible contenant l’identité.
Les appelants doivent tester ce résultat avant de chercher le Node :

```cpp
auto added = graph.add<MyNode>(argumentsDuConstructeur);
if (!added) {
    // Traiter added.error() sur contrôle.
    return;
}
Node* borrowed = graph.node(*added);
```

`node(id)` retourne un pointeur emprunté ou `nullptr` pour une identité absente,
invalide ou retirée du graphe souhaité. Le lookup mutable sert aux opérations
de contrôle sur un Node au repos ; il n’autorise pas une mutation de son état
DSP simultanée à son traitement. Le lookup const ne transfère pas davantage
de propriété. Les deux recherches n’allouent pas et ne prennent pas de verrou.

## Identités, transaction et capacité

Les identités sont uniques dans un DAG, dans `[1, UINT32_MAX]`, et jamais
réutilisées pendant sa durée de vie, même après suppression et collecte. Chaque
DAG démarre à un ; une identité ne désigne pas un objet d’un autre DAG.

La séquence interne utilise un curseur `uint64_t` pour représenter exactement
`UINT32_MAX + 1`. Avant toute conversion vers NodeID, elle rejette zéro et toute
valeur au-delà de `maxNodeID`. Le candidat est lu sans être consommé ; il n’est
validé qu’après construction et insertion réussies. Le constructeur du dérivé
doit préserver l’ID du Node de base ; une identité différente est rejetée.

L’ordre de l’opération est : contrôle du domaine et du quota, construction dans
un `unique_ptr<Node>` provisoire, vérification de l’identité, insertion du
propriétaire, puis validation du curseur. Tout objet provisoire est détruit sur
contrôle en cas d’échec. Le graphe et les anciens plans restent inchangés.

Le quota `maxOwnedNodes` borne le nombre d’objets actuellement possédés,
**Node souhaités et Node en retrait différé compris**. Zéro est admis et interdit
tout ajout. Le quota est indépendant du nombre d’identités déjà émises ; libérer
une place permet un ajout avec un nouvel ID, jamais un ancien. La capacité
représentable du conteneur est aussi vérifiée avant insertion.

| Erreur | Cause |
|---|---|
| NodeIDExhausted | Domaine d’identités épuisé, avant toute conversion réductrice |
| NodeCapacityExceeded | Quota d’objets possédés ou capacité de stockage atteints |
| AllocationFailed | `bad_alloc` pendant construction/insertion ou sécurisation du retrait |
| NodeConstructionFailed | Autre exception issue du constructeur dérivé |
| InvalidNodeIdentity | Constructeur dérivé ignorant l’identité attribuée |

Ces codes sont ajoutés en fin d’énumération. `add` transforme les exceptions de
construction/allocation en erreurs `expected` ; il n’introduit aucune exception
dans le callback. Le constructeur utilisateur ne doit ni réentrer le DAG,
publier un ID/pointeur provisoire, ni modifier un Node actif. Ses effets externes
et la consommation d’arguments déplacés ne sont pas annulables par le DAG.

## Propriété, adresses et retrait

| Donnée | Type / propriétaire | Durée de vie et droits |
|---|---|---|
| Node souhaités | `vector<unique_ptr<Node>>`, DAG | Contrôle propriétaire ; seuls les handles se déplacent lors des insertions/effacements |
| Node retirés empruntés | `vector<unique_ptr<Node>>`, même DAG | Possession conservée jusqu’au dernier emprunt, puis collecte sur contrôle |
| Tâches des plans | `Node*` non propriétaires | Lecture/traitement selon le contrat Node ; aucun transfert de propriété |
| Jetons d’emprunt | État opaque du Node, partagé avec les plans | Copies/relâchements sur contrôle ; ne possèdent jamais le Node |
| Curseur d’identité | `uint64_t`, séquence privée du DAG | Contrôle uniquement, avancé après insertion réussie |
| Quota | `size_t`, DAG | Fixé à la construction, contrôle uniquement |
| Lookup externe | `Node*` / `const Node*` | Adresse stable tant que l’objet est vivant ; aucune prolongation automatique de sa durée de vie |

Le conteneur de propriétaires est un vecteur. Ses réallocations et le décalage
de ses éléments ne déplacent jamais les objets pointés ; un plan déjà compilé
garde exactement ses adresses et sa liste de tâches.

Pour respecter la durée de vie exigée par cette fiche, `remove` transfère un
Node emprunté dans le stockage de retrait **avant** de modifier l’appartenance
au graphe, les arêtes ou le marqueur output. Si cette sécurisation échoue,
l’opération retourne une erreur et laisse le graphe intact. Après succès,
`node(id)` retourne `nullptr` et les nouvelles compilations l’excluent ; les
anciens plans peuvent encore le traiter. Sans emprunt, la destruction peut
être immédiate sur contrôle ; les usages de pointeurs externes doivent alors
avoir cessé avant `remove`.

`collectRetiredNodes()` détruit uniquement les Node retirés dont **tous** les
plans ont libéré les jetons, et retourne le nombre de destructions. La retraite
d’un seul plan, sa copie ou son remplacement ne suffit pas si un autre plan
emprunte encore le Node. La libération d’un jeton ne détruit pas le Node : la
collecte reste explicitement sur contrôle après quiescence. Les utilisations
externes de pointeurs bruts doivent avoir cessé avant cette collecte.

Cette évolution remplace le refus historique `NodeInUse` de S01-07 ; le code
reste réservé dans l’énumération pour compatibilité. Le protocole interthreads
Ready/Pending/Active/Retired et les scénarios exhaustifs de S02-06 restent à
livrer dans leurs fiches respectives. Aucun ACK de publication n’est simulé ici.
Le propriétaire doit toujours survivre à tous les plans.

## Validation exécutée

Compilation C++26 réussie avec Clang 19.1.7/libc++19, CMake 4.3.4 et Ninja.
**124/124 tests CTest passent** : 111 tests existants adaptés au résultat de
`add` et au retrait différé, plus 11 tests de stockage/identités et deux tests
d’injection d’échecs d’allocation. Aucun test n’est désactivé.

Les tests couvrent les types mixtes, les arguments transmis, les deux lookups,
les identités absentes, 512 insertions et un effacement intermédiaire avec
adresses inchangées, le quota incluant les retraits, les exceptions de
constructeur, l’identité incorrecte et la non-réutilisation. La séquence
réellement utilisée par le DAG est testée directement aux limites exactes
`UINT32_MAX - 1`, `UINT32_MAX`, `UINT32_MAX + 1`, zéro et `UINT64_MAX`, sans
allouer des milliards d’objets ni exposer un réglage du curseur du DAG.

L’injection fait échouer successivement chaque allocation d’un ajout, y compris
l’insertion après construction complète du dérivé. Elle vérifie le nettoyage,
l’absence de Node partiel, le même ID lors d’une nouvelle tentative et le
fonctionnement du plan préexistant. Un autre test force l’échec du stockage de
retrait et vérifie la conservation du Node, des arêtes, des marqueurs et des
anciens plans. Les tests de durée de vie vérifient la destruction polymorphe
unique sur le thread propriétaire et les emprunts de plusieurs plans/copies.

Les tests RT précédents vérifient toujours zéro allocation/libération C++ dans
les fenêtres de `process` et d’exécution de 64 callbacks du graphe préparé.
L’injection d’échec et l’instrumentation restent dans l’exécutable de test,
jamais dans la bibliothèque.

Une seconde compilation avec `-fsanitize=address,undefined`,
`-fno-omit-frame-pointer` et `-fno-sanitize-recover=all` passe également les
**124/124 tests**, avec `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1` et
`UBSAN_OPTIONS=halt_on_error=1`, sans diagnostic d’accès mémoire, de comportement
indéfini ou de fuite. LeakSanitizer est exécuté hors du sandbox qui empêche son
inspection des processus ; aucune instrumentation n’est désactivée dans ce test.

## Reproduire dans l’environnement préparé

```bash
source /workspace/.mka-setup/activate.sh
cmake -S /workspace/mka-audio-dsp -B /workspace/.mka-build/s02-01 -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/workspace/.mka-setup/toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
  -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/workspace/.mka-build/native-tests/_deps/googletest-src
cmake --build /workspace/.mka-build/s02-01 --parallel 4
ctest --test-dir /workspace/.mka-build/s02-01 --output-on-failure --no-tests=error
```

Pour reproduire la seconde compilation, conserver les mêmes options CMake,
utiliser un répertoire de build distinct et ajouter :

```bash
-DCMAKE_CXX_FLAGS='-stdlib=libc++ -fsanitize=address,undefined -fno-omit-frame-pointer -fno-sanitize-recover=all'
```

Définir ensuite les deux variables de sanitizers ci-dessus pour la compilation
(la découverte GoogleTest exécute les binaires) et pour CTest. Le runtime
`libclang-rt-19-dev` doit être disponible dans l’outillage LLVM local.
