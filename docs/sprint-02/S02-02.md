# Sprint 2, fiche 2 — S02-02 : Connection et stockage des arêtes

**État : implémentée, en attente de validation utilisateur.**
Source : [Trello #10](https://trello.com/c/Ds9AYM8Q). S02-01 est validée dans la
conversation. Cette étape livre uniquement S02-02 ; le tableau Trello n’est pas
modifié.

## Valeur publique et identité

Le nouveau module `mka.audio.dsp.connection`, réexporté par DAG et ExecutionPlan,
fournit :

```cpp
struct Connection {
    ChannelID from{};
    ChannelID to{};
    constexpr bool operator==(const Connection&) const noexcept = default;
};
```

L’agrégat concret est copiable trivialement et possède deux valeurs 64 bits,
sans pointeur, allocation, propriété de Node ou buffer audio. `from` représente
toujours le producteur Out ; `to` représente le consommateur In/Aux. L’égalité
compare exactement les deux ChannelID complets, avec leurs champs Node, port et
indice. Deux liaisons entre les mêmes Node sur des canaux différents restent
deux arêtes distinctes. In et Aux de même indice sont des destinations distinctes.

Une valeur seule ne valide aucune structure : `{}` vaut `{0,0}` et peut être
copiée ou modifiée indépendamment d’un graphe. Même après destruction du DAG,
une copie reste une valeur numérique lisible ; elle ne garde aucun Node vivant
et ne permet pas d’accéder à une ancienne instance. Seule l’insertion dans DAG
contrôle la validité structurelle.

## Stockage et consultation

DAG possède un `vector<Connection>` privé. Les Node ne stockent pas ces arêtes.
La croissance du conteneur ne déplace pas les Node ; la réorganisation des
propriétaires de Node ne change pas les couples stockés. L’ordre d’insertion
des arêtes est conservé.

```cpp
std::span<const Connection> DAG::connections() const noexcept;
```

Ce lookup est une vue empruntée en lecture seule, réservée au contrôle. Le DAG
possède les éléments ; toute édition du graphe peut invalider le span et les
références vers ses éléments. Pour conserver un instantané indépendant, copier
les valeurs avant l’édition. Ne pas lire cette vue simultanément à une mutation.
L’observation n’alloue pas et ne prolonge aucune durée de vie.

Les recherches de doublon, d’occupation, de chemin et le tri topologique lisent
désormais les ChannelID stockés. Les opérations de suppression/déconnexion
existantes décodent les NodeID à partir de ces mêmes valeurs. La compilation
préparée consomme directement un `span<const Connection>`, sans tableau de
conversion intermédiaire. `detail::PlanConnection` reste un alias du type public
pour compatibilité ; il ne définit plus une seconde représentation.

## Insertion et limites de cette fiche

La structure acceptée conserve les règles existantes : Out → In/Aux, Node
présents, destination libre, absence de cycle et de doublon exact. Un Out peut
alimenter plusieurs destinations. Les indices logiques absents de Config et
les layouts vides restent admis. Le rôle output et les entrées backend ne
créent aucune arête ; aucune identité matérielle artificielle n’est introduite.

**Convention temporaire :** cette fiche conserve l’appel existant
`connect(source, destination)` pour les deux surcharges. La convention
`connect(destination, source)` citée par Trello appartient explicitement au
livrable S02-03 et sera harmonisée dans cette prochaine fiche. Les champs de
Connection désignent toujours les rôles du signal, indépendamment de cet ordre
d’arguments. Aucun adaptateur n’accepte silencieusement les deux conventions.
Les noms d’erreurs existants (`ConnexionAlreadyExists`, `ChannelAlreadyConnected`,
etc.) restent en place jusqu’aux fiches qui traitent ces opérations.

L’adaptateur historique `connect(Channel, Channel)` conserve ses champs larges
à la frontière : directions contrôlées d’abord, existence des Node sur 64 bits,
puis indices avec `toChannelIndex`. Une valeur NodeID supérieure à UINT32_MAX
ne peut pas devenir un autre Node par troncature ; un indice supérieur à 65535
est refusé par `InvalidChannelIndex` avant insertion. Ce refus intervient
désormais à `connect`, car le nouveau stockage doit être exactement encodable.

Les allocations de recherche/insertion restent sur contrôle. `bad_alloc` devient
`AllocationFailed`, une capacité de conteneur non représentable devient
`ConnectionCapacityExceeded`. Les refus s’effectuent avant insertion et la
collection souhaitée reste inchangée. Le chemin audio n’utilise pas la vue de
stockage du DAG : un plan garde ses rôles et liaisons préparés, indépendants des
éditions ultérieures. Aucun verrou, attente ou gestion de propriété n’est ajouté
au callback.

La déconnexion précise par deux ChannelID et son retour idempotent
`expected<bool>` restent S02-05. Ici, la déconnexion historique retire toujours
la première arête de la paire de NodeID, comme auparavant. Les validations
complètes des fiches suivantes ne sont pas déclarées livrées par cette migration.

## Validation exécutée

Compilation C++26 réussie avec Clang 19.1.7/libc++19, CMake 4.3.4 et Ninja.
**136/136 tests CTest passent**, sans test ignoré ou désactivé : les 124 tests
précédents (dont le rejet legacy avancé à l’insertion), 11 nouveaux tests de
valeur/stockage et un test d’injection d’échecs d’allocation de connexion.

Les assertions statiques vérifient l’agrégat, les types de champs, la copie et
destruction triviales, l’égalité constexpr/noexcept, l’alias de préparation et
la vue const. Les tests dynamiques couvrent l’identité sur 64 bits, les canaux
et ports distincts entre mêmes Node, les doublons, le fan-out, l’occupation,
les layouts vides et l’absence d’arêtes backend. Ils vérifient la croissance
des deux conteneurs indépendants, 128 arêtes conservées exactement, les copies
détachées, les bornes larges avant conversion et l’instantané d’un ancien plan.

Le test d’injection fait échouer successivement chaque allocation d’un ajout
d’arête, puis vérifie collection, adresses, rôles et plans inchangés. Après une
nouvelle tentative réussie, l’ancien plan conserve son résultat (`103`) et une
nouvelle compilation reflète la liaison (`106`). Les tests RT précédents
conservent zéro allocation/libération C++ dans leurs fenêtres de traitement.

Une seconde compilation passe aussi les **136/136 tests sous ASan/UBSan**, avec
détection des fuites activée, sans diagnostic mémoire ou comportement indéfini.
Options : `-fsanitize=address,undefined -fno-omit-frame-pointer
-fno-sanitize-recover=all`, `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1` et
`UBSAN_OPTIONS=halt_on_error=1`. LeakSanitizer a été exécuté hors de la restriction
ptrace du sandbox. Le runtime `libclang-rt-19-dev` est disponible dans l’outillage
LLVM local ; aucune instrumentation n’est désactivée dans ces tests.

Une revue indépendante du stockage, des parcours, de la préparation et des
durées de vie des vues n’a trouvé aucun défaut bloquant. `git diff --check` passe.
