## API livrée

Dans le module public existant `mka.audio.dsp.channel`, namespace
`mka::audio::dsp` :

```cpp
enum class PortType : std::uint16_t { In = 0, Out = 1, Aux = 2 };

constexpr bool isInputPort(PortType port) noexcept;
constexpr bool isOutputPort(PortType port) noexcept;
constexpr bool isValidPort(PortType port) noexcept;
```

`In` est l’entrée principale, `Out` la sortie et `Aux` une entrée
auxiliaire/sidechain dont le sens audio appartient au Node. Aucun de ces ports
ne représente une voie matérielle. Les valeurs 0/1/2 sont désormais explicites
et le type sous-jacent est exactement `std::uint16_t` (16 bits).

| Port | `isInputPort` | `isOutputPort` | `isValidPort` |
|---|---|---|---|
| `In` (0) | true | false | true |
| `Out` (1) | false | true | true |
| `Aux` (2) | true | false | true |
| Toute représentation de 3 à 65535 | false | false | false |

Les helpers sont `[[nodiscard]]`, totaux, purs et `constexpr noexcept` :
uniquement des comparaisons, aucune allocation, exception, synchronisation ou
lecture backend. Ils inspectent la valeur 16 bits reçue ; un cast d’un entier
plus large peut déjà avoir tronqué sa valeur avant l’appel et ne remplace donc
pas une validation de plage. Les valeurs décodées hors enum doivent être
validées avant usage ; aucun contrôle dynamique n’est ajouté dans
`Node::process`.

## Validation de direction dans le DAG

`DAG::connect(const Channel& from, const Channel& to)` retourne explicitement
`std::expected<void, GraphError>` et n’autorise que les couples suivants :

| Source → destination | In | Out | Aux |
|---|---|---|---|
| In | refus | refus | refus |
| Out | accepté si les autres contraintes du graphe le permettent | refus | accepté si les autres contraintes du graphe le permettent |
| Aux | refus | refus | refus |

Tout autre couple, y compris un code inconnu dans l’une ou les deux positions,
retourne `GraphError::InvalidDirection` **avant** les vérifications d’existence,
de doublon, de cycle et d’occupation. Cette priorité est voulue : une mauvaise
direction doit toujours être signalée comme telle, même si d’autres erreurs
coexistent. Aucun parcours allouant du graphe n’a lieu sur ce chemin de rejet.
Le graphe reste inchangé.

Pour une direction valide, les autres validations et leurs erreurs restent
inchangées. L’opération complète reste sur le thread de contrôle, potentiellement
allouante et non `noexcept` ; elle n’est pas appelée depuis le callback audio.

### Compatibilité des erreurs

`GraphError` est un alias public de l’énumération existante `ErrorType`, pas une
deuxième énumération. `Result` reste donc exactement compatible avec
`std::expected<void, GraphError>`. `InvalidDirection` est ajouté en fin
d’énumération pour préserver les codes existants. `InvalidPort` reste défini
pour compatibilité, mais `connect` retourne désormais `InvalidDirection` pour
les directions illégales, conformément à la fiche.

La taille publique de `PortType` passant de 8 à 16 bits, tous les consommateurs
doivent être recompilés. Le build complet réalisé ici recompile tous les modules
et leurs consommateurs.

## Validation exécutée

Build C++26 complet avec Clang 19.1.7/libc++19, CMake 4.3.4 et Ninja : réussi.
CTest : **23 tests passent**, soit les 7 tests de S01-01 et **16 nouveaux tests**
pour S01-02, sans test ignoré ou désactivé.

- Assertions statiques du sous-jacent exact, des valeurs, de l’enum fortement
  typée, de l’API des helpers `bool(PortType) noexcept`, des résultats
  `constexpr` (notamment 3 et 65535), et du type de retour de `connect`.
- Classification des **65 536 représentations** par chacun des trois helpers.
- Table indépendante des **9 couples officiels**, dont Out → Aux accepté.
- Codes invalides 3, 4, 255, 256, 32768 et 65535 dans chaque position et dans
  les deux positions simultanément. Le cas 256 détecte notamment une
  régression vers l’ancien sous-jacent 8 bits.
- Après chaque rejet sur un graphe vide d’arêtes : aucune arête n’est
  déconnectable ; une connexion légale ultérieure réussit et se déconnecte
  exactement une fois.
- Sur un graphe déjà connecté : 23 couples illégaux combinant les ports
  officiels et deux codes invalides ne créent pas d’arête, ne suppriment pas
  l’arête existante et ne la dupliquent pas. Les observations utilisent
  `connect`/`disconnect`, sans ajouter d’accès public au stockage privé pour
  les tests.
- Priorité d’`InvalidDirection` en présence d’un nœud absent, d’une entrée
  occupée, d’une auto-boucle ou d’un chemin inverse.
- Conservation des erreurs existantes pour les directions valides : nœud
  absent, doublon, cycle et entrée occupée ; In/Aux restent des destinations
  distinctes au même numéro de canal.

La revue de code indépendante n’a relevé aucun problème bloquant.
`git diff --check` passe.

## Reproduire dans l’environnement préparé

```bash
source /workspace/.mka-setup/activate.sh
cmake -S /workspace/mka-audio-dsp -B /workspace/.mka-build/s01-02 -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=/workspace/.mka-setup/toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
  -DFETCHCONTENT_SOURCE_DIR_GOOGLETEST=/workspace/.mka-build/native-tests/_deps/googletest-src
cmake --build /workspace/.mka-build/s01-02 --parallel 4
ctest --test-dir /workspace/.mka-build/s01-02 --output-on-failure --no-tests=error
```

Cette fiche ne livre ni l’encodage de `ChannelID`, ni les descripteurs de
buffers, ni les nouvelles interfaces de Node/Config/ProcessContext. Elle ne
modifie pas la politique d’allocation des NodeID ni l’algorithme de tri
topologique ; les limites d’intégration connues restent distinctes du contrat
des ports testé ici. Aucun comportement de traitement audio n’est revendiqué.
