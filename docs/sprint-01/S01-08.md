## Utilisation

Le graphe possède les Node ; les plans les empruntent selon le contrat de
S01-07. Le marquage et la préparation se font en contrôle :

```cpp
Result DAG::markAsOutput(NodeID id);
std::expected<ExecutionPlan, ErrorType> DAG::compile(const BackendConfig&) const;

struct BackendConfig {
    FrameCount maxFrames = 0;
    std::size_t inputChannels = 0;
    std::size_t outputChannels = 0;
};

struct BackendBlock {
    std::span<const float* const> inputs;
    std::span<float* const> outputs;
    FrameCount frames = 0;
};

bool ExecutionPlan::exec(const BackendBlock&) noexcept;
```

`inputChannels`/`outputChannels` sont les capacités physiques maximales ; les
spans du callback contiennent toutes les voies **réellement fournies**. Un bloc
avec moins de voies est admis. Un processeur qui choisit une voie matérielle
doit vérifier qu’elle est disponible, sans supposer que son layout la fournit.
Les entiers larges du driver doivent être contrôlés avant conversion vers
FrameCount. Aucun NodeID ou ChannelID matériel n’est créé.

`markAsOutput` rejette un NodeID absent par `GraphError::NodeNotFound`. Il est
idempotent et ne réserve aucune voie physique. Il n’empêche ni les arêtes
sortantes ni la combinaison source + sortie. Le marqueur est nettoyé lors de la
suppression du Node et pris en instantané par chaque nouveau plan ; un ancien
plan garde ses rôles tant qu’il reste utilisé.

`compile()` sans argument reste une compilation structurelle, utile pour les
tests de graphe et d’emprunts. Ce plan refuse l’exécution audio tant qu’il n’a
pas été préparé ; `isBackendPrepared()` permet de vérifier cet état.

## Rôles déterminés à la compilation

| Rôle | inputs | auxiliary | outputs | backendOutputs |
|---|---|---|---|---|
| Source non marquée | Toutes les entrées backend | Logiques | Logiques | Vide |
| Non-source non marquée | Logiques | Logiques | Logiques | Vide |
| Source marquée sortie | Toutes les entrées backend | Logiques | Logiques | Toutes les sorties backend |
| Non-source marquée sortie | Logiques | Logiques | Logiques | Toutes les sorties backend |

Une source n’a **aucune arête entrante In/Aux**, même vers un canal absent des
layouts. Son `layoutInput` ne filtre jamais les entrées matérielles : un layout
vide reçoit lui aussi toutes les voies du callback, en `const float*`.

Les nœuds marqués voient toutes les sorties physiques dans l’ordre backend,
quel que soit leur layout de sorties logiques. Le code de `process` choisit
librement les voies et les samples écrits. Les descripteurs matériels ont
`channel == 0`, ignoré ; la voie est leur position dans le span.

Les sorties logiques restent des buffers privés du plan et ne sont jamais
remplacées par une sortie physique. Une sortie marquée peut alimenter un ou
plusieurs successeurs tout en écrivant directement vers le matériel. Les
samples d’entrée sont const ; les spans de descripteurs const empêchent la
réaffectation de leurs pointeurs mais autorisent l’écriture des floats de sortie.

## Stockage et liaison logique nécessaires à ce chemin

La préparation alloue les descripteurs et un buffer distinct par sortie logique
déclarée. L’ordre des layouts est conservé ; les liaisons utilisent les identités
de canaux et non leurs positions dans le vecteur. Les inputs/auxiliaires non
alimentés, ou reliés à une sortie non produite, lisent un slot silence dédié,
initialisé en contrôle et jamais écrit pendant le callback.

Les arêtes vers des canaux hors layout restent structurellement admises. Une
arête historique Channel dont l’indice dépasse 65535 était refusée, à la
livraison de S01-08, lors de la préparation audio avant toute conversion
réductrice. [S02-02](../sprint-02/S02-02.md) avance ce rejet à `connect` pour
ne stocker que des identités numériques représentables. Les outputs logiques sont remis à zéro
pour les frames courantes afin qu’un processeur qui n’écrit pas ne fasse pas
relire le bloc précédent à ses successeurs.

Ce stockage constitue le chemin minimal nécessaire à S01-08 : il n’effectue pas
de recyclage de slots, calcul de liveness, in-place, PDC ou publication A/B.
La correction locale du tri producteur → consommateur est nécessaire pour
fournir les samples aux successeurs. Les couches conservent l’ordre stable par
NodeID ; les oracles exhaustifs des sprints suivants ne sont pas revendiqués.

## Callback, silence et priorité des écritures

Après les gardes de forme/pointeurs, `exec` :

1. Rebind les tableaux de descripteurs physiques possédés par le plan sur les
   pointeurs de ce callback, avec identité zéro.
2. Met **toutes les sorties physiques à zéro**, une seule fois, pour le nombre
   effectif de frames, y compris si aucun Node n’est marqué ou si le graphe est vide.
3. Exécute chaque Node selon l’ordre topologique stable, via un ProcessContext
   local construit avec les rôles préparés et les vues matérielles courantes.
4. Efface les pointeurs matériels des descripteurs du plan avant de retourner.

Tous les écrivains marqués voient les mêmes adresses physiques. Il n’y a ni
mixage implicite ni remise à zéro entre deux Node : **le dernier write effectif
gagne par sample/canal**. Un écrivain qui ne touche que les frames paires laisse
les frames impaires écrites précédemment intactes. Les voies qu’aucun Node
n’écrit restent au silence.

Aucun tableau n’est redimensionné, alloué ou libéré par le callback. Les
pointeurs/descripteurs du driver restent empruntés jusqu’au retour ; chaque
callback utilise ses adresses, même si elles changent. Les Node ne doivent pas
les conserver. Le backend reste propriétaire des samples ; le plan possède les
tableaux de descripteurs et le stockage logique.

## Gardes et erreurs

Un plan non préparé, des frames/voies dépassant les capacités ou un pointeur
physique nul avec frames positives entraînent `false` avant tout appel de Node
et sans accès aux samples. Un bloc valide suivant fonctionne normalement.
`frames == 0` est un no-op accepté si la forme est admissible, sans Node appelé.
Sur rejet, les samples sont inchangés ; le propriétaire du callback peut les
mettre au silence avec sa propre capacité sûre, sans que le plan parcoure un
nombre de frames excessif.

La préparation retourne des erreurs structurées pour les liens invalides, les
Node absents, les indices non encodables, les configurations invalides, les
tailles non représentables (`PreparationCapacityExceeded`) et un ordre de
tâches incohérent (`InvalidExecutionOrder`). Elle laisse un état déjà préparé
inchangé en cas d’échec. Les nouveaux codes sont ajoutés en fin d’énumération.
Les allocations en contrôle peuvent toujours produire les exceptions standard
de ressources ; aucun budget mémoire métier n’est introduit ici.

La surcharge de compatibilité `exec(const ProcessContext&)` utilise uniquement
`inputs` et `backendOutputs` comme vues physiques. `auxiliary` et `outputs`
doivent être vides ; elle ne confond pas un contexte logique de Node avec un
callback backend. Les identités fournies pour ces vues physiques sont ignorées.

## Durée de vie et copies

La préparation, copie, affectation, déplacement et destruction des plans se
font en contrôle après quiescence de leurs usages. Les copies possèdent leurs
propres buffers logiques et réparent leurs pointeurs internes ; les déplacements
transfèrent l’état préparé, laissant la source non préparée. Les jetons S01-07
continuent de protéger la suppression des Node.

Le DAG doit survivre aux plans. Les plans copiés partagent les Node/DSP, pas les
buffers : leur traitement reste séquentiel et ne fournit pas une garantie de
traitement concurrent d’un même effet. `exec` n’est pas réentrant. Les spans
doivent référencer des descripteurs/pointeurs valides ; les buffers non nuls
consommés couvrent les frames courantes. Les entrées physiques ne doivent pas
chevaucher la mémoire modifiable des sorties ou du plan. Les raw pointers ne
permettent pas de vérifier universellement ces durées de vie et étendues.

La validation fonctionnelle utilise de vrais graphes/plans/Node sur des buffers
de callback en mémoire, sans dépendance à un SDK ou périphérique audio.

## Validation exécutée

Compilation C++26 réussie avec Clang 19.1.7/libc++19, CMake 4.3.4 et Ninja.
**111 tests CTest passent**, sans test ignoré ou désactivé : les 87 tests
précédents, 23 tests fonctionnels backend et un test RT sur le graphe préparé.

Les nouveaux tests couvrent les rôles source/sortie, les layouts vides, la
lecture et l’écriture multivoies, les adresses physiques directes et leur
changement entre callbacks. Ils vérifient aussi la séparation logique/matériel,
les successeurs et le fan-out, les auxiliaires, les indices logiques dispersés,
le silence initial et le dernier write effectif par sample. Les cas d’échec
incluent les dépassements, les pointeurs nuls, les liens invalides et la
préservation d’un état préparé ; les copies et déplacements gardent des buffers
et emprunts valides.

Le test RT instrumente les opérations C++ `new`/`delete`, avec un témoin positif
qui vérifie le détecteur. Il mesure **zéro allocation et zéro libération C++**
pendant 64 callbacks aux adresses de sortie alternées et un rejet pour
dépassement de frames. Les assertions et la destruction des ressources restent
hors de cette fenêtre de mesure. Cette instrumentation ne prétend pas détecter
tous les allocateurs tiers ou appels système d’un effet utilisateur.
