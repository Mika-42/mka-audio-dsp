# Fiche #6 — S01-06 : ProcessContext et vues audio

**État : proposition implémentée, en attente de validation utilisateur.**
Cette étape livre uniquement S01-06. Les fiches #1 à #5 sont validées par
l’utilisateur. Le tableau Trello n’est pas modifié.

## Contrat public exact

Le module `mka.audio.dsp.process_context` réexporte les descripteurs et alias
du module channel et expose dans `mka::audio::dsp` :

```cpp
struct ProcessContext {
    std::span<const InputChannel> inputs;
    std::span<const InputChannel> auxiliary;
    std::span<const OutputChannel> outputs;
    std::span<const OutputChannel> backendOutputs;
    FrameCount frames = 0;
};
```

L’agrégat est concret, non polymorphe, copiable sans allocation et non
propriétaire. `frames` adopte réellement le contrat 32 bits des fiches
précédentes : c’est le nombre effectif d’échantillons par canal, dans
`[0, maxFrames]`, jamais une taille maximale de boucle par défaut.

Les spans const empêchent un Node de réaffecter les pointeurs ou les identités
des descripteurs. Les inputs/auxiliary restent `const float*` ; les samples
d’outputs/backendOutputs restent modifiables via leurs `float*`, sans const_cast.
Les sorties logiques sont distinctes des sorties matérielles : donner accès au
backend ne remplace jamais un buffer logique encore utilisé par un successeur.

## Binding préparé et contexte local au callback

`PreparedContextBindings` contient uniquement les vues **internes** stables,
les bornes et les rôles déterminés par l’appelant lors de la préparation :

```cpp
struct PreparedContextBindings {
    std::span<const InputChannel> inputs;
    std::span<const InputChannel> auxiliary;
    std::span<const OutputChannel> outputs;
    FrameCount maxFrames = 0;
    std::size_t maxBackendInputChannels = 0;
    std::size_t maxBackendOutputChannels = 0;
    bool isSource = false;
    bool isOutput = false;
};

Result validateContextBindings(const PreparedContextBindings&) noexcept;
```

Cette validation préparatoire retourne `NullBuffer` si un pointeur interne
sélectionné est nul avec `maxFrames > 0`. Les inputs internes sont ignorés pour
une source, puisqu’ils seront remplacés par les inputs backend du callback.
Auxiliary et outputs restent internes et sont toujours contrôlés. Avec
`maxFrames == 0`, les pointeurs nuls sont admissibles puisque seul un callback
vide sera accepté. Aucun sample n’est lu, aucune mémoire n’est allouée.

Les capacités effectives des buffers et descripteurs sont établies hors RT par
leur propriétaire. Le helper ne peut mesurer l’étendue d’un buffer raw-pointer.
Les bindings ne doivent **jamais contenir de vues matérielles temporaires**.

`withProcessContext` reçoit ces bindings, les deux spans backend courants,
`frames` et un consommateur `void(const ProcessContext&) noexcept` :

```cpp
const bool accepted = withProcessContext(
    prepared, currentInputs, currentOutputs, frames,
    [&node](const ProcessContext& context) noexcept {
        node.process(context);
    });
```

Le consommateur est contraint à la compilation à retourner exactement void et
à être noexcept. Aucun `std::function` ni stockage dynamique n’est utilisé.
Ses restrictions RT (aucune allocation, attente, synchronisation bloquante,
exception, I/O/log) et l’interdiction de conserver les pointeurs restent un
contrat de l’implémentation du consommateur.

Le contexte est une variable locale, consommée de manière synchrone : le helper
ne stocke aucune adresse backend dans les bindings ou dans un état persistant.
Chaque appel reçoit les nouvelles adresses, sans réallocation ni copie de
samples. L’appelant doit maintenir les descripteurs et samples vivants jusqu’au
retour du consommateur, qui ne doit retenir ni contexte ni pointeur matériel.

### Sélection des vues

| Rôle préparé | inputs | auxiliary | outputs | backendOutputs |
|---|---|---|---|---|
| Interne ordinaire | internes | internes | internes | vide |
| Source seule | tous les inputs backend, dans l’ordre physique | internes | internes | vide |
| Sortie seule | internes | internes | internes | toutes les sorties backend, dans l’ordre physique |
| Source + sortie | tous les inputs backend | internes | internes | toutes les sorties backend |

Aucun layout ne filtre ces vues matérielles. Un Node source avec un
`Config::layoutInput` vide reçoit toujours l’intégralité du span backend.
Un Node de sortie conserve ses outputs internes, même avec des successeurs.
Les deux rôles sont indépendants ; aucune arête matérielle ni ChannelID
artificiel n’est créé. Les descripteurs backend sont fournis par l’appelant
avec `channel == 0` (ignoré) ; seule leur position désigne la voie physique.

## Gardes de callback et fail-safe

Le dimensionnement et la préparation restent hors RT. L’appel effectif vérifie
ensuite ses tailles courantes contre ces bornes préparées, avant d’exposer le
contexte au Node :

- `frames > maxFrames` : false, aucun consommateur invoqué et aucun sample lu
  ou écrit.
- Trop de voies backend **sélectionnées** pour la capacité préparée : même
  rejet. Les vues backend non utilisées par les rôles sont ignorées.
- Pointeur nul dans une des quatre vues sélectionnées avec frames positives :
  false avant invocation, sans toucher aux samples ni aux descripteurs.
- `frames == 0` avec tailles admissibles : true, aucun consommateur invoqué et
  aucun sample consulté, même si les pointeurs sont nuls.
- Callback admissible suivant : les seules adresses fournies pour cet appel
  sont utilisées, sans état d’erreur persistant.

Ces gardes sont bornées par les capacités préparées et les vues internes fixes.
Elles ne compilent pas de graphe ni ne préparent de nouvelle capacité en RT.
Le résultat booléen constitue un refus léger, sans construire de diagnostic
allouant dans le callback. Un span vide est valide : il n’y a alors aucun sample
de ce port à consommer.

Le fail-safe ne tente pas de parcourir les buffers avec un frames excessif,
ce qui pourrait provoquer le dépassement à éviter. Il laisse les samples
inchangés ; la mise au silence des sorties externes revient au propriétaire
du callback, qui connaît leur capacité réelle. L’initialisation générale des
sorties backend reste au routage ultérieur.

## Limites d’intégration

Les rôles sont des **métadonnées fournies par l’appelant**. Cette fiche ne livre
ni la détection topologique des sources, ni `DAG::markAsOutput`, ni la compilation
des tâches, ni l’implémentation d’`ExecutionPlan::exec`, ni un backend matériel.
Elle fournit le contexte et le binding que ces étapes pourront appeler.
Les tests de rôles invoquent de vrais dérivés de Node via le helper, mais ne
prétendent pas exécuter un plan compilé du DAG.

Les spans/raw-pointers ne garantissent pas la capacité réelle des samples,
leur durée de vie ou l’absence d’alias accidentel entre sorties internes et
matérielles. Ces obligations restent à la charge du propriétaire. Le helper
préserve les deux vues distinctes fournies ; il ne peut rendre disjoints des
buffers que l’appelant a fait se chevaucher.

## Validation exécutée

Compilation C++26 complète réussie avec Clang 19.1.7/libc++19, CMake 4.3.4 et
Ninja. **69 tests CTest passent**, soit les 54 tests précédents et **15 nouveaux
tests**, sans test ignoré ou désactivé. `git diff --check` passe.

- Assertions statiques des cinq champs exacts, types des spans et de FrameCount,
  agrégat non polymorphe, copie/destruction triviales et constance des samples.
- Vérification à la compilation des consommateurs : void/noexcept accepté,
  consommateur potentiellement lançant ou à retour non void rejeté.
- Préflight interne : refus des pointeurs nuls sans modification des bindings,
  inputs internes ignorés pour une source, préparation nulle admise à maximum zéro.
- Quatre combinaisons de rôles avec invocation de vrais Node via le helper,
  identité et ordre des pointeurs, inputs complets malgré un layout vide,
  sorties matérielles disponibles seulement pour le rôle sortie.
- Producteur marqué sortie avec consommateur logique : le successeur lit le
  buffer interne et les samples backend restent distincts.
- Frames zéro : aucun consommateur ni sample consulté ; zéro voie avec des
  frames positives : contexte vide accepté.
- Dépassements de frames ou de voies sélectionnées : aucun consommateur appelé,
  sentinelles inchangées et prochain callback admissible accepté.
- Pointeur nul dans chacune des vues sélectionnées : rejet avant consommation,
  sans modification des samples internes ou matériels.
- Descripteurs backend locaux à deux callbacks successifs : seules les adresses
  courantes sont utilisées, anciens samples inchangés, bindings sans rétention
  de ces vues après destruction des descripteurs du callback.

La revue de production indépendante n’a relevé aucun problème bloquant. Les
tests n’annoncent pas une intégration de plan compilé ou de backend matériel.
