# Fiche #5 — S01-05 : Config et layouts des canaux traités

**État : validée par l’utilisateur dans la conversation.**
Cette fiche a été livrée seule, après les fiches #1 à #4. L’avancement des
fiches suivantes figure dans le suivi du sprint. Le tableau Trello n’est pas
modifié.

## Structure et signification

Le nouveau module public `mka.audio.dsp.config` réexporte les alias fondamentaux
et fournit dans `mka::audio::dsp` :

```cpp
struct Config {
    std::vector<ChannelIndex> layoutInput;
    std::vector<ChannelIndex> layoutAuxiliary;
    std::vector<ChannelIndex> layoutOutput;
};
```

Il s’agit d’un agrégat valeur concret, copiable, non abstrait, sans héritage,
`virtual`, `final` ou API RTTI. Chaque vecteur possède ses indices. Les numéros
désignent des **canaux logiques traités**, pas des positions physiques backend.
L’ordre de déclaration est conservé pour la future préparation des contextes :
un layout `{6, 2, 65535}` n’est pas trié ni réinterprété comme `{0, 1, 2}`.

Les ports sont indépendants : un indice peut apparaître sur In, Aux et Out,
mais ne doit pas être répété dans un même layout. Tous les ChannelIndex de 0 à
65535 sont valides ; vérifier les entiers larges avec `toChannelIndex` **avant**
conversion/insertion pour éviter une troncature préalable.

## Validation publique hors RT

```cpp
inline constexpr std::size_t maxLayoutChannels = 65536;
Result validateConfig(const Config& config) noexcept;
```

`Result` est `std::expected<void, ErrorType>`. Les nouveaux codes sont ajoutés
en fin d’énumération pour conserver les valeurs existantes :

| Cas | Résultat |
|---|---|
| Layouts vides, épars ou dans un ordre arbitraire | Succès |
| Même indice présent sur plusieurs ports | Succès |
| 65 536 indices distincts dans chacun des trois ports | Succès |
| Plus de 65 536 entrées dans un port | `LayoutCapacityExceeded` |
| Indice répété dans un port de capacité admissible | `DuplicateChannelIndex` |

La capacité est le domaine intrinsèque de ChannelIndex : **65 536 valeurs**,
incluant zéro. Ce n’est ni une limite cumulée des trois ports, ni une capacité
matérielle/backend. Les tailles sont des `size_t`, jamais des indices 16 bits.
Les ports sont contrôlés dans l’ordre entrée/auxiliaire/sortie ; dans chaque
port, la capacité est vérifiée avant les doublons.

Un bitmap fixe de 65 536 bits (8 Kio) sert au contrôle de chaque port. Le parcours
est linéaire, sans allocation dynamique ni tri, et ne modifie ni les vecteurs
ni leurs éléments. Le validateur ne lance pas d’exception, ne verrouille pas
et ne réalise pas d’I/O. Il s’utilise en préparation/contrôle, pas dans `process`.

En revanche, construire/copier/modifier les vecteurs peut allouer et produire
les exceptions standard d’allocation. Ces opérations ne sont pas déclarées
`noexcept` et doivent rester hors du thread audio. Le validateur ne capture pas
une allocation qui a échoué avant son appel et ne promet pas qu’une copie
ultérieure réussira.

## Configuration possédée par Node

L’ancien Config imbriqué fondé sur l’enum Layout est remplacé par le type
public. `Node::Config` est conservé comme **alias** de ce même type, pas comme
une seconde structure. L’ancienne enum `Node::Layout` n’est plus utilisée :
un layout stéréo se déclare désormais `{0, 1}`.

Node copie les trois vecteurs lors de sa construction en contrôle et expose :

```cpp
const Config& config() const noexcept;
```

La copie ne dépend plus de la durée de vie ni des mutations ultérieures du
Config fourni par l’appelant. L’accesseur ne copie pas, n’alloue pas et renvoie
une référence empruntée valable pendant la durée de vie de l’objet Node.
Le constructeur perd son ancien `noexcept`, puisque cette copie peut allouer.

**Précondition explicite :** appeler `validateConfig` et traiter son erreur
avant de construire un Node avec une configuration externe. Le constructeur
ne fait pas lui-même cette validation et ne renvoie pas de `expected`.

La configuration utilisée par un plan doit rester stable. Le retour `const&`
empêche l’édition par cet accesseur, mais ne constitue pas un protocole de
publication ni une protection contre une affectation concurrente de Node.
Toute édition/remplacement/destruction reste coordonnée en contrôle ; aucune
réallocation ni mutation concurrente n’est autorisée pendant `process`.

Les signatures d’id, channel et process restent inchangées. Aucun mécanisme de
préparation universelle, de latence ou de publication de Node n’est ajouté.

## Ce que Config ne filtre pas

`DAG::connect` ne consulte pas Config : une arête valide sur un canal absent
des layouts reste autorisée. Les tests le vérifient sur In/Aux, avec un indice
65535 et des layouts vides ou épars. Aucune restriction de layout n’est ajoutée.

Le contrat des sources reste : une source topologique reçoit toutes les entrées
backend, même si `layoutInput` est vide. **Le raccordement effectif des buffers
backend n’est pas livré par cette fiche** : il relève de S01-06/S01-08. Les tests
actuels vérifient l’absence de filtrage structurel ; ils ne simulent pas une
intégration backend inexistante. ProcessContext et ExecutionPlan sont inchangés.

Le fixture des tests de ports et la déclaration stéréo de l’exemple historique
sont adaptés à la forme vectorielle de Config. L’exemple n’est pas une cible
du build ; les tests de cette fiche utilisent leurs propres dérivés concrets.

## Validation exécutée

Compilation C++26 complète réussie avec Clang 19.1.7/libc++19, CMake 4.3.4 et
Ninja. Lors de la livraison de S01-05, **54 tests CTest passent**, soit les 42 tests précédents et **12 nouveaux
tests**, sans test ignoré ou désactivé. `git diff --check` passe.

- Types exacts des trois vecteurs, Config agrégat concret non final et
  non polymorphe, copie potentiellement allouante et signature `expected` du
  validateur ; `Node::config()` renvoie exactement `const Config& noexcept`.
- Layouts vides, épars et non triés, indices 0 et 65535 conservés dans l’ordre.
- Même indice autorisé dans trois ports indépendants.
- Doublons adjacents ou séparés dans chaque port : erreur structurée et données
  inchangées, y compris un doublon dans une liste de capacité exactement 65536.
- Domaine complet de 65 536 indices accepté par chaque port, puis dans les trois
  ports simultanément ; 65 537 éléments refusés dans chaque port avant le test
  des doublons.
- Copies Config avec stockage indépendant ; snapshot Node inchangé après
  modification du Config de l’appelant et toujours valide après destruction
  d’un Config temporaire.
- Connexions structurelles In/Aux vers le canal 65535 accepté hors layouts,
  avec des layouts vides ou épars, sans filtrage du DAG.

La revue de code indépendante n’a relevé aucun problème bloquant. La
validation préalable à la construction et la stabilité des configurations
actives restent des obligations explicites de l’appelant.
