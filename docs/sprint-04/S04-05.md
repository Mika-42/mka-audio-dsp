# S04-05 — Exécution RT et fail-safe

L’API canonique reste public void exec(const mka::audio::AudioProcessContext&)
noexcept, sans seconde méthode process. La publication d’une génération précède
exec et reste la responsabilité du propriétaire. Le plan actif ne consulte que
ses opérations préparées ; aucune traversée du DAG, recherche de ChannelID,
allocation/libération, journalisation, attente ou mutex n’entre dans le callback.

Avant toute tâche, exec vérifie préparation, maxFrames, nombres de voies,
capacités de samples annoncées et pointeurs non nuls consommés. Un refus ne lit
aucun input et ne modifie aucun slot interne : les sorties externes non nulles
sont mises à zéro sur min(frames,outputCapacityFrames), même si leur nombre
dépasse la capacité préparée. L’appelant garantit les tailles réelles des tableaux
et buffers. Les adaptateurs bool historiques utilisent maxFrames comme borne
conservatrice de silence sur refus ; le contexte canonique permet de déclarer
la capacité réelle, y compris plus petite que frames. Aucune API ne peut déduire
la taille d’une allocation à partir d’un pointeur brut.

Un callback accepté efface les sorties physiques une fois, lie les entrées
backend aux sources et les sorties backend aux Nodes marqués, écrit ctx.frames
et appelle chaque Node une fois dans l’ordre compilé. frames=0 exécute les
opérations sans accès aux samples ; les pointeurs nuls y sont permis. Le LWW
physique porte sur chaque sample effectivement écrit : aucun effacement entre
les writers. Les sorties logiques restent distinctes et disponibles aux
successeurs. Toutes les vues externes sont vidées à la fin du callback.

CallbackDiagnostic définit des bits numériques sticky. callbackDiagnostics
lit le diagnostic ; takeCallbackDiagnostics le draine atomiquement. Le uint32
atomique est exigé toujours lock-free par static_assert. Les opérations relaxed
ne publient ni samples ni durée de vie ; elles permettent seulement un relevé
concurrent sans data race. Les refus de préparation sur contrôle préservent le
diagnostic ; une préparation réussie le remet à zéro. Les copies conservent une
valeur indépendante, le déplacement transfère les bits et vide l’ancien objet.
Le traitement/formatage des erreurs reste sur contrôle.

Les fenêtres RT instrumentent new/delete et, sur Linux, les appels directs à
pthread_mutex_lock/trylock/timedlock via le linker. Un témoin explicite prouve
que l’interception de mutex fonctionne ; aucun wrapping n’affecte la bibliothèque
ou les applications clientes. Les tests ne prétendent pas intercepter les appels
internes d’une bibliothèque partagée tierce. Les règles de Node::process restent
applicables aux processeurs personnalisés. Toute préparation/copie/retraite
exige la quiescence du plan ; le DAG conserve les Nodes empruntés.
