# S06-01 — Capacités backend fixes

`BackendConfig` est une valeur concrète dont inputChannels/outputChannels,
sampleRate (Hz) et maxFrames sont uint32_t. Le champ maxFrames conserve sa
position initiale pour les initialiseurs désignés existants. Une fréquence zéro
signifie non renseignée ; le moteur n'impose pas de fréquence matérielle.
`makeBackendConfig` valide les valeurs larges avant toute conversion réductrice.
`ExecutionPlan::backendConfig()` rend une copie optionnelle du snapshot préparé,
sans moyen de modifier la configuration active.

Les descripteurs physiques sont préparés sur contrôle et les pointeurs rebindés
sans copie audio. Chaque callback doit maintenant annoncer **exactement** les
nombres de voies préparés, même avec zéro frame ; l'ancien contrat « au plus la
capacité » est remplacé. Un manque/excès de voies, un bloc trop long ou un buffer
nul non vide refuse tout process et produit un diagnostic atomique. Le silence
de refus reste borné aux capacités mémoire explicitement annoncées. Les appels
zéro frame à forme exacte acceptent des pointeurs nuls sans les déréférencer.

Une nouvelle forme matérielle exige une préparation sur contrôle, jamais un
resize en audio. Les tests historiques faisant varier les comptes préparent
désormais la configuration correspondante avant les callbacks ; les tests de
refus larges utilisent la factory vérifiée, sans tronquer SIZE_MAX vers uint32_t.

Tests dédiés : 0/1/2/6 voies, fréquence capturée malgré les edits du caller,
adresses changeantes, capacité maximale, bloc max+1 et canaris, manque/excès de
voies, pointeur manquant, forme zéro frame invalide, overflow de chaque valeur
large et refus de préparation conservant l'ancien snapshot.
